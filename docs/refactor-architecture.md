# PHP 代码诊断 RAgent 重构架构方案

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 版本 | 1.0 |
| 日期 | 2026-11-10 |
| 适用项目 | `php-diagnostic-ragent` |
| 参考材料 | 知识星球 Ragent 项目专栏、公开仓库 `nageoffer/ragent` |
| 重构目标 | 在不改变现有 HTTP API 和诊断行为的前提下，将单体执行链拆成可扩展的 Agentic RAG 分层 |
| 实施计划 | [`docs/refactor-implementation-plan.md`](refactor-implementation-plan.md) |

本文吸收参考项目的架构原则，不照搬其 Java、AgentScope、Elasticsearch、LightRAG、RustFS、
RocketMQ 和 Langfuse 技术栈。当前项目继续使用 Python、FastAPI、Celery、Redis、PostgreSQL
和只读 PHP 仓库访问，以现有业务事实和证据约束为最高优先级。

## 2. 重构结论

当前系统已经具备可运行的企业级诊断闭环，包括异步任务、通用代码检索、符号索引、配置反查、
调用链、只读验证、确定性业务分析、AI 证据约束叙写、SSE、反馈、评测和 Prometheus 指标。
本次重构不是重写，而是把已经验证过的能力重新分层，解决持续扩展时的结构性问题。

核心决策如下：

1. `worker.py` 只保留 Celery 适配和任务入口，诊断编排迁入独立应用服务；
2. `business_analysis.py` 拆成共享证据模型、分析器契约和按业务能力注册的分析器；
3. 检索从“单个函数按顺序调多个辅助函数”升级为“通道 + 预算 + 后处理器链”；
4. 每次诊断形成统一 `DiagnosisContext`，取消、超时、证据预算和追踪在阶段边界统一处理；
5. LLM 只承担证据约束下的叙写，不获得任意 Shell、SQL、文件写入或生产变更权限；
6. 新增结构化 Trace，SSE、审计、指标和评测共享同一阶段事件来源；
7. 外部 API、数据库现有任务结果结构和前端主流程保持向后兼容，通过适配层逐步迁移。

## 3. 当前问题诊断

### 3.1 已具备的能力

- `app/diagnosis.py` 提供任务创建、查询、取消、重试、历史、报告和 SSE；
- `app/worker.py` 提供 Celery 队列、软硬超时、检索、验证和报告闭环；
- `app/query_understanding.py` 从问题中提取可组合业务概念和显式代码符号；
- `app/retrieval_planner.py` 负责支撑门禁、候选排序、动态发现和配置定义词；
- `app/php_index.py`、`app/symbol_tools.py` 提供符号、引用和调用链能力；
- `app/business_analysis.py` 从源码证据生成确定性事实；
- `app/llm_diagnosis.py` 提供证据引用校验、结构化输出、缓存和 AI 元数据；
- `app/reporting.py`、`app/ai_evaluation.py`、`app/metrics.py` 提供报告、评测和监控；
- 迁移、鉴权、审计、备份、预检、发布门禁和前端工作台已经形成生产闭环。

### 3.2 主要结构债务

| 问题 | 当前表现 | 影响 |
|---|---|---|
| Worker 过重 | `app/worker.py` 约 1698 行，同时承担队列、检索、排序、证据选择、验证和报告 | 单点改动影响面大，难以按阶段测试和追踪 |
| 分析器单体 | `app/business_analysis.py` 约 2737 行，多个业务分析器与通用辅助函数混在一起 | 新增业务能力容易继续堆叠，评审和复用成本高 |
| 检索边界不稳定 | 首轮检索、概念扩展、符号补全、配置定义和调用链由编排函数直接串联 | 无法按通道独立测试、降级、计时和替换 |
| 后处理耦合 | 去重、排序、门禁、证据预算同时散落在 planner、worker 和 analyzer | 新增排序策略或证据门禁时容易重复修改 |
| 缺少统一运行上下文 | 各阶段依赖局部变量和数据库重复读取 | 取消检查、时间预算、Trace 和结果组装不一致 |
| SSE 与执行事实分离 | 前端主要轮询任务状态，SSE 结束后再补偿查询 | 无法直接展示检索、分析、AI 和验证各阶段耗时 |
| 评测偏最终结果 | 已有 AI 证据引用与诊断基线，但缺少检索阶段指标 | 难以判断质量下降来自召回、排序、分析还是生成 |

### 3.3 重构约束

- 不允许为完整问题增加类、方法、表或答案的硬编码映射；
- 不允许把没有源码或只读运行态证据的推测写成业务事实；
- 不修改被诊断的 `waky3`、`waky4`、`waky6` 业务仓库；
- 不改变现有 API 路径、请求字段、任务状态和报告关键字段；
- 不在重构阶段同时替换数据库、消息队列、检索存储或前端框架；
- 每个阶段必须可独立回滚，不能采用一次性大爆炸迁移；
- 所有新增代码、配置和迁移继续遵守中文上下文注释规则。

## 4. 目标架构

### 4.1 逻辑分层

```text
┌──────────────────────────────────────────────────────────────┐
│ API 层：鉴权、参数校验、任务命令、查询和 SSE                   │
├──────────────────────────────────────────────────────────────┤
│ 应用层：DiagnosisPipeline、阶段状态、取消/超时和结果组装        │
├──────────────────────────────────────────────────────────────┤
│ 领域层：问题画像、证据、事实、置信度、分析器注册表              │
├──────────────────────────────────────────────────────────────┤
│ 能力层：查询理解、检索通道、后处理、只读工具、模型网关          │
├──────────────────────────────────────────────────────────────┤
│ 基础设施层：PostgreSQL、Redis、代码仓库、LLM HTTP 和 Celery     │
├──────────────────────────────────────────────────────────────┤
│ 可观测层：Trace、SSE 事件、审计、指标和离线/在线评测            │
└──────────────────────────────────────────────────────────────┘
```

依赖方向只能从外层指向稳定的领域契约。领域分析器不能直接访问 Celery、FastAPI 或数据库连接池。

## 5. 核心领域模型

### 5.1 DiagnosisContext

`DiagnosisContext` 是单次诊断唯一可变上下文，至少包含：

| 字段 | 作用 |
|---|---|
| `task_id`、`project`、`question` | 任务身份和原始业务问题 |
| `started_at`、`deadline_at` | 阶段预算和软超时协调 |
| `profile` | 业务概念、显式符号、模块范围和问题类型 |
| `retrieval_budget` | 查询数、候选数、读取窗口和最终证据上限 |
| `channel_results` | 各检索通道结果、耗时、错误和降级原因 |
| `evidence` | 已回源码验证的去重证据 |
| `findings` | 确定性事实和证据引用 |
| `validation` | 只读数据库、配置和日志验证结果 |
| `warnings` | 可展示但不导致任务失败的问题 |
| `trace` | 当前运行的阶段 ID、父子关系和状态 |

所有阶段在开始和结束时检查取消状态与剩余预算。任何阶段失败都写结构化错误类型，不能只保存原始异常文本。

### 5.2 检索契约

```text
SearchChannel
  ├─ name / enabled / priority / timeout
  ├─ search(DiagnosisContext) -> ChannelResult
  └─ health() -> ChannelHealth

ChannelResult
  ├─ channel / hits / elapsed_ms
  ├─ degraded / error_type
  └─ metadata

SearchPostProcessor
  ├─ order / enabled(context)
  └─ process(hits, context) -> hits
```

首期通道包括：

- `CodeTextChannel`：中文业务锚点、显式符号和精确源码词；
- `SymbolChannel`：类、方法、配置键和定义行；
- `ConfigDefinitionChannel`：真实配置定义和数值；
- `CallChainChannel`：入口到校验、扣款、转账等业务节点的受限链路；
- `DocumentChunkChannel`：现有文档分块全文与向量兼容结果；
- `HistoryChannel`：历史诊断摘要，仅作提示，不能替代当前源码事实；
- `ValidationChannel`：只读数据库、配置和日志验证计划。

后处理器顺序固定为：去重、来源归因、业务相关度排序、跨概念覆盖、支撑门禁、证据预算和最终裁剪。

### 5.3 分析器契约

确定性分析器不接收完整问题并返回固定答案，而是声明能力条件：

```text
DiagnosticAnalyzer
  ├─ analyzer_id
  ├─ requires: 概念、动作、证据类型
  ├─ supports(lines, profile) -> bool
  └─ analyze(lines, profile) -> Finding[]
```

注册表按可组合特征匹配分析器，例如“注册 + 设备 + 数量”或“提现 + 手续费 + 最低金额”。
具体类名、方法名、配置值和阈值仍必须从当前项目索引、源码或只读验证动态取得。

### 5.4 Finding 与 Assessment

每条事实必须包含：

- 结构化结论；
- 证据引用 `file:line`；
- 事实类别和置信度；
- 由哪个分析器生成；
- 支持该事实的配置、校验或调用关系；
- 证据边界和不能证明的内容。

最终 `Assessment` 只负责聚合置信度、缺失证据和下一步建议，不重新推导业务事实。

## 6. 诊断执行流水线

```text
加载任务与幂等检查
  ↓
问题理解：概念、符号、模块和问题类型
  ↓
初始检索与支撑门禁
  ├─ 支撑不足：保存缺口报告，结束
  └─ 支撑足够：继续
      ↓
      动态发现：符号、配置键、调用链和文档
      ↓
      通道检索与后处理
      ↓
      源码验证与证据裁剪
      ↓
      分析器注册与确定性事实
      ↓
      可选只读运行态验证
      ↓
      可选 LLM 证据约束叙写
      ↓
      报告评估、持久化和终态事件
```

每个阶段产生统一事件：

```json
{
  "task_id": "diag_xxx",
  "stage": "retrieval",
  "status": "COMPLETED",
  "progress": 55,
  "elapsed_ms": 1830,
  "summary": {"channels": 4, "hits": 92, "degraded": 1},
  "trace_id": "trace_xxx"
}
```

## 7. Agent 执行边界

参考项目使用 ReAct Agent 和 MCP 扩展工具。本项目首期不开放自由 ReAct，也不接入可写 MCP，
原因如下：

- 核心场景是高可信源码诊断，确定性检索和证据门禁优先；
- 自由推理循环会放大重复扫描、超时和成本；
- 当前工具均为内部只读能力，直接协议化不会提高业务正确率；
- 诊断结论必须可复现、可审计，不能依赖模型决定是否跳过高价值检索。

首期采用受约束的 Plan-Act-Observe：

1. 规划器只能基于问题画像选择已注册只读通道；
2. 每轮观察结果必须产生新的真实符号、配置键、文件或明确缺口；
3. 没有新增有效线索时停止，不允许改写关键词继续空转；
4. 最大轮数、总查询数、读取窗口和时间均由预算控制；
5. LLM 只在证据收集完成后进行叙写，不决定证据是否存在。

后续需要跨项目、多工具或多轮追问时，再在相同通道和预算契约上增加 Agent 编排，不改变底层能力。

## 8. 模型网关与稳定性

当前 `llm_diagnosis.py` 已具备协议适配、结构化输出、证据引用校验、缓存和超时。重构后增加独立模型网关：

- `ModelGateway` 统一调用入口，业务层不感知供应商协议；
- 支持候选模型顺序和按任务选择，不在 Prompt 中写模型差异；
- 首包超时、总超时、空响应和可重试 HTTP 错误分类；
- 只对幂等模型请求重试，避免流式输出重复拼接；
- 熔断状态存 Redis，按模型和 Endpoint 隔离；
- 所有降级写入 Trace 和 `ai_metadata`；
- 确定性报告不因模型不可用而失败。

模型路由是后续增强项，不应阻塞前三个结构重构阶段。

## 9. Trace、SSE 与评测

### 9.1 Trace

新增诊断运行 Trace：

- Run：任务、项目、问题摘要、总耗时、终态和预算；
- Span：阶段、通道、分析器、验证工具和模型调用；
- 输入摘要：仅保存脱敏后的查询、文件范围和计划；
- 输出摘要：命中数、证据数、事实数、错误类型和 token usage；
- 父子关系：支持从报告事实反查检索通道和分析器。

Trace 不保存密钥、完整配置、Cookie、Token、SQL 参数或无关源码。

### 9.2 SSE

SSE 直接消费阶段事件，并保留现有任务查询作为断线恢复来源。事件类型至少包括：

- `task.started`；
- `stage.started`、`stage.completed`、`stage.degraded`；
- `retrieval.summary`；
- `analysis.summary`；
- `ai.started`、`ai.completed`、`ai.skipped`；
- `task.completed`、`task.failed`、`task.cancelled`。

### 9.3 评测

评测分为四层：

| 层级 | 指标 |
|---|---|
| 查询理解 | 概念覆盖、显式符号召回、误扩展率 |
| 检索 | 文件召回、证据行命中、配置值召回、通道降级率 |
| 确定性分析 | 事实覆盖、错误事实率、证据引用完整率 |
| AI 与报告 | 证据引用召回、结论一致性、token、延迟和人工正确率 |

评测集不能保存“完整问题到固定答案”的映射；期望值应描述证据文件、符号、配置键、关键事实类别和负向控制。

## 10. 兼容与迁移策略

### 10.1 外部兼容

- 保持 `/api/diagnoses` 和现有请求/响应字段；
- 保持任务状态、进度和结果中的检索审计字段；
- 保持报告 Markdown 和证据下载能力；
- 保持 Celery 任务名 `app.worker.run_diagnosis_task` 和队列；
- 新字段只追加，不删除旧字段；废弃字段经过至少一个发布周期。

### 10.2 内部迁移

采用 Strangler 模式：

1. 先建立契约和特征测试；
2. 抽出新模块；
3. 旧入口委托新模块；
4. 新旧实现对照运行；
5. 测试和真实任务无回归后移除旧代码。

### 10.3 数据库迁移

Trace 表、分析器元数据和通道指标使用追加式迁移。不得在首个重构发布中重命名或删除现有表字段。

## 11. 风险与控制

| 风险 | 控制 |
|---|---|
| 大文件拆分改变证据顺序 | 增加固定输入输出特征测试和真实任务对照 |
| 分析器注册导致错误命中 | 使用正负向回归集和可组合特征门禁 |
| 通道并行增加磁盘压力 | 首批保持代码通道串行，仅文档、历史和验证允许受控并发 |
| SSE 事件重复或丢失 | 事件 ID、任务状态快照和幂等前端恢复 |
| Trace 泄露业务数据 | 字段级脱敏、摘要存储和访问控制 |
| 模型降级被误判为业务失败 | 分离 `deterministic_status` 和 `ai_status` |
| 重构范围过大 | 每阶段独立发布、可回滚、禁止跨阶段混交 |

## 12. 完成标准

重构完成需要同时满足：

- `worker.py` 只保留队列和任务适配，不再包含检索排序与分析主体；
- 诊断流水线可通过阶段契约单测，不启动 Celery 也能执行；
- 检索通道和后处理器有独立测试、耗时、降级和审计字段；
- `business_analysis.py` 不再包含全部业务分析器；
- 每个事实可追溯分析器、证据和验证来源；
- SSE 可输出阶段事件，并保留断线恢复；
- 固定正负向评测集无通过率下降；
- 真实 waky3、waky4、waky6 回归任务结论与证据保持正确；
- 注释覆盖、全量测试、编译、前端语法、Compose、迁移和发布门禁全部通过。
