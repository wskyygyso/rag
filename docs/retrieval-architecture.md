# RAgent 通用代码检索架构

## 1. 目标

RAgent 的检索层用于回答“这个业务规则在源码哪里、由什么条件控制、是否有配置值或运行态证据”，不是为每个已经问过的完整问题保存一条实现映射。

核心约束：

1. 问题解析只提取可复用的业务概念、中文业务锚点和用户显式给出的代码符号；
2. 类名、方法名、配置键和表名必须从当前项目索引或源码中动态发现；
3. 没有足够业务支撑时停止扩展，明确报告缺口，不用泛词拼出“看似完整”的答案；
4. 所有结论必须回到当前源码行、配置定义或只读验证结果；
5. 新增业务问法不应要求复制整条调用链，也不应保存“完整问题 → 固定类/方法/表”的答案模板。

## 2. 处理流水线

```text
用户问题
  └─ 问题理解：中文业务片段、显式符号、可组合概念
      └─ 首轮源码检索：PHP 注释、配置、文档和业务文本
          └─ 检索支撑门禁
              ├─ 不足：停止扩展，证据数 0，返回补充业务对象/入口/符号的建议
              └─ 足够：继续
                  ├─ 动态符号与配置发现
                  ├─ 配置键反向定位定义值
                  ├─ 子仓收敛与候选排序
                  ├─ 静态调用链补全
                  ├─ 证据窗口分层裁剪
                  ├─ 源码守卫与确定性分析
                  └─ 受证据约束的 LLM 叙写
```

## 3. 问题理解

问题理解由 `app/query_understanding.py` 负责：

- 提取概念，例如“钻石 + 提现 + 手续费”；
- 生成概念对应的通用中英文检索词；
- 保留用户直接给出的 `Class::method`、配置键或其他显式符号；
- 不生成项目专属 `Control.php`、`Model.php`、SQL 表名或完整调用链。

概念词条只描述基础业务词汇和动作。一个词条应能服务多个问法，例如“手续费”既可用于提现，也可用于兑金币；不能把“某项目提现完整问题”绑定到若干具体方法。

## 4. 检索支撑门禁

`app/retrieval_planner.py` 的 `assess_retrieval_support()` 决定是否允许继续扩展。

满足任一条件才可继续：

1. 生产源码命中至少一个四字以上中文业务锚点；
2. 问题包含显式代码符号；
3. 同一源码命中同时覆盖足够的概念；问题包含两个以上领域概念时，至少两个领域概念
   必须共现。

以下组合不能触发扩展：

- `用户 + 阈值`；
- `配置 + 状态`；
- `设备 + 用户 + 数量`，但缺少“注册”动作；
- 只命中 `return false`、`if`、`user` 等泛化结构或单词；
- 只命中文档、语言包或后台展示但没有生产业务承载。

无支撑时统一返回：

- `retrieval_mode=insufficient_support`；
- `retrieval_support.grounded=false`；
- `evidence=[]`；
- `deterministic_findings.facts=[]`；
- 提示用户补充业务对象、页面入口、类方法或配置键。

## 5. 动态发现

首轮命中后，系统从当前项目符号索引发现：

- 类、接口、Trait；
- `Class::method`；
- `Config::get(...)` 读取的配置键；
- 命中文件对应的高相关服务文件。

完整点号配置键通常只能证明“代码读取了该配置”。为避免知道键名却不知道值，系统还会提取末级字段名并回到配置目录定位真实定义行，例如：

```text
anchor.diamond_to_usd
  → Config::get 调用点
  → 末级字段 diamond_to_usd
  → php/config/anchor.php 的 'diamond_to_usd' => ...
```

这个过程由配置索引和源码定义全文驱动，不依赖某个项目的固定配置映射。

首轮命中经常落在异常日志行，而真正的 `Config::get()` 调用位于相邻几行。系统会为高排名
命中读取一个受限制的只读源码窗口，从 `content + context` 提取真实配置键后再回查定义。
这使“日志命中、配置值上一行、校验条件下一行”的常见链路能够闭合，同时不会为每条搜索结果
读取整个文件。

### 5.1 项目符号索引快照复用

完整 PHP 符号索引不再由每个诊断任务重复扫描和重写。`app/project_index_cache.py` 使用
PHP 文件相对路径、字节数和纳秒修改时间生成代码快照指纹，并按
`项目 + 指纹` 缓存 gzip JSON 索引：

- 命中 Redis 时直接复用符号、引用、配置和 SQL 索引；
- 同一快照首次构建使用 Redis 单飞锁，其他 Worker 等待同一结果；
- 收获锁后再次读取缓存，避免重复构建；
- Redis 故障、缓存损坏或等待超时回退真实扫描，不阻断诊断；
- PostgreSQL 只在该快照尚未持久化时重写四万级符号表，避免并发任务无意义重写；
- 代码文件变化产生新指纹和新缓存键，旧快照不会继续作为当前源码事实。

实现中的缓存键不包含仓库绝对路径；任务结果记录 `cache_status`、`cache_wait_ms`、
`build_ms`、`fingerprint` 和 `cache_key`，便于排查缓存未命中、等待和降级原因。

## 6. 批量检索、继承证据与候选收敛

完成动态符号和配置发现后，检索词通过 `search_code_terms()` 一次批量扫描，而不是为每个词
重复遍历整个仓库。`term_search` 记录检索词数、候选数和耗时；候选上限只影响排序输入，
最终证据仍压缩到 64 条，不会随时间扩大模型上下文。

显式类问题会先从完整符号索引确认目标文件，并使用问题中的模块词、首轮高排名路径和精确
符号证据排除其他模块的同名类。随后只沿真实 `extends` 声明补充一级直接基类。

基类证据不是默认全部进入事实：

1. 目标类已有足够事实且问题要求的累计、消耗、清理等动作均已出现时，父类仅作为已验证信息；
2. 目标类缺少问题明确询问的动作时，只有真正包含该动作的父类才进入确定性分析；
3. 结论范围按最终事实实际引用的文件计算，避免把 `getType`、`__destruct`、
   `getInstance` 等通用基础设施方法误写成业务规则；
4. 父类未覆盖缺失动作时，报告保留“当前目标类未观察到该动作”的证据边界。

显式目标类事实另有类别配额和动作覆盖权重。大量同类 `if` 不能挤掉时间、配置、积分、奖励、
锁和 Key 等不同类别；同一问题同时询问多个动作时，每类动作分别影响排序。

## 7. 调用链与证据预算

调用链只用于补齐从入口到最近业务校验、扣款和转账方法的源码。调用链节点必须与入口处于同一业务子仓，并过滤框架、语言包、测试和依赖目录。

当前预算：

| 项目 | 上限 | 作用 |
|---|---:|---|
| 通用召回候选 | 200 | 发现下一轮应搜索的真实符号 |
| 聚焦通用命中 | 36 | 进入符号/配置关联阶段 |
| 动态扩展词 | 24 | 避免全仓无限扩展 |
| 总检索词 | 36 | 包含原文锚点和配置定义词 |
| 最终证据 | 64 | 控制持久化、Redis 和 LLM 上下文 |
| 高可信通用证据 | 28 | 保留配置段、方法入口和业务注释 |
| 配置定义证据 | 8 | 回答阈值、比例、费率等真实值 |
| 调用链证据 | 12 | 优先保留入口及最近两级业务调用 |

最终选择不是“先到先得”：业务锚点、配置定义、调用链浅层节点和每个规划词的确定性命中都有独立保留空间，再用通用相关度补足剩余名额。

## 8. 回答生成边界

确定性分析只解释已经取得的源码：

- 配置值必须来自配置定义；
- 业务分支必须来自真实条件、调用或返回值；
- 调用链缺失时只能说明当前证据边界；
- 不能因为目录、类名或关键词相似就断言业务规则；
- LLM 只能使用已提供证据，引用不存在的文件或行号时整段结果应被拒绝。

没有证据时，“回答不上来”是合法结果。系统应说明缺口并停止扩展，而不是自动增加关键词映射。

## 9. 扩展规则

新增能力时按以下顺序处理：

1. 先判断现有通用概念是否已覆盖问题；
2. 增加可复用的名词、动作或代码词，而不是完整问句模板；
3. 增加从索引、配置定义或源码结构发现候选的能力；
4. 增加证据验证和确定性解释；
5. 用至少一个真实项目和多个问题回归；
6. 同步更新测试、架构文档、验证证据和 `progress.md`。

禁止：

- 为单个完整问题维护固定类/方法/表列表；
- 用问题文本直接决定业务结论；
- 用大量弱相关命中掩盖业务锚点缺失；
- 在没有源码证据时让 LLM 补全事实。

## 10. 观测字段

诊断结果中的 `retrieval_plan` 用于解释检索行为：

- `retrieval_mode`：`semantic_discovery` 或 `insufficient_support`；
- `retrieval_support`：支撑等级、直接锚点数、概念覆盖和门禁原因；
- `semantic_concepts`：问题中识别出的可组合概念；
- `discovered_queries`：从索引发现的真实符号和配置键；
- `config_definition_queries`：用于回查配置定义值的末级字段名；
- `discovery_sources`：每个扩展词来自哪个文件、行号和阶段；
- `verified_explicit_symbols`：已从当前符号索引验证的问题显式类、方法或配置标识；
- `explicit_target_files`：问题实际指向的目标类文件；
- `inherited_target_files`：沿真实 `extends` 声明验证过的直接基类，不表示全部进入事实；
- `term_search`：批量精确检索的 `query_count`、`match_count` 和 `elapsed_ms`；
- `project_index`：项目索引 `cache_status`、等待时间、构建耗时和代码快照指纹；
- `symbol_persistence`：该代码快照是否需要重写 PostgreSQL 符号索引。

任何新增检索机制都应能通过这些字段解释“为什么继续”或“为什么停止”。
